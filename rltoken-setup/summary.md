# 2. Torch 编译推理延迟（2026-11-07，统一 10 步复测）

## 测试条件

- **共同条件**：RTX 4090 D · π0.5 step5000 · batch=1 · BF16 模型 · CPU 4 线程 · 两路 224×224 全零图像和全零 state · 10 步去噪。各组预热 5 次、GPU 同步计时 30 次，采用 `torch.inference_mode()`，计入模型输入／输出转换；不含 Env、Ray、相机、动作执行或训练更新，未连接机械臂。三类模型路径依次测试，不并行占用 GPU。
- **PI05／RTC PI05**：预测 20 步、解码返回 10 步；不执行 RLT encoder／decoder，也不执行 MLP。RTC 使用 `approx`、`clip=5`、固定 bootstrap 前序动作、`executed_horizon=2`、`delay_steps=2`。
- **RLT**：冻结 step5000 提取特征、生成 20 步参考动作并计算 `z_rl`，配套在线运行 `20261104-230711` 的 step15000 MLP 输出 10 步动作；包含 MLP 与路由，不运行 RLT decoder。沿用历史基准的 `mode="train"` rollout 采样口径，但不做梯度计算或训练更新；Stage2 评测的均值动作模式与此有区别。

# 3. 权重同步后清理耗时（2026-10-28）

## 测试条件

- **配置与范围**：RTX 4090 D · 4 步去噪、仅去噪编译 · 实际 MLP patch 构建/应用后推理；收发端通过单进程队列连接，保留自动 GC，不含 Ray 网络传输、训练、replay 和机械臂。

## 核心结果

| 测试阶段 | 次数 | GC 平均耗时 | 显存缓存清理 | 权重应用 + 清理 + 推理 |
|---|---:|---:|---:|---:|
| 每次同步后强制清理 | 100 | 178.99 ms | 5.92 ms | 268.33 ms |
| 不强制清理 | 1000 | 不调用 | 不调用 | 82.82 ms |
| 恢复强制清理 | 100 | 178.13 ms | 5.99 ms | 267.44 ms |

- **耗时**：三组推理均约 74 ms，省去的是约 **185 ms** 的同步后清理；单独复测 20 次，GC/显存缓存清理均值为 175.60/5.93 ms。
- **内存与正确性**：不强制清理的 1000 次中，已分配显存保持 9509.77 MiB，预留显存由 9998 增至 10020 MiB 后稳定，CPU RSS 增加约 0.16 MiB；定期权重一致性及逐次版本、动作有限值检查通过。

- **数据来源**：[同步 A/B 逐次数据](support/benchmarks/20261028/rlt_cleanup_ab.json)、[20 次清理复测](support/benchmarks/20261028/rlt_gc_recheck.json)。

## 结论与采用方案

- **采用方案**：当前 UR 配置默认 `rollout.cleanup_after_weight_sync=false`，跳过同步后的强制 GC 和显存缓存清理，保留自动 GC；设为 `true` 恢复。
- **验证边界**：长期在线内存稳定性仍待验证；上述收益不代表每个 chunk 都缩短 185 ms。

# 4. 在线 RLT 三 Worker 时间基线（2026-10-30）

## 测试条件

- **测试配置**：UR5e · 单张 RTX 4090 D · π0.5 + RLT，冻结 Stage 1 step 5,000 权重；4 步参考动作去噪、仅去噪编译；`continuous_tracking=false`、前台 `step_frequency=20` Hz、每个执行 chunk 为 3 个动作。训练 `global_batch_size=micro_batch_size=256`，单 GPU 梯度累积为 1。
- **计时口径**：采用 `20261030-211110` 的 `detailed` 本机经过时间，不增加 GPU 同步，数值不是精确 GPU kernel 耗时。Learner 分为预热稳定更新、episode 动作执行窗口之外、episode 运行期间；后两阶段用于观察单 GPU 训练与推理竞争，运行期间也包含动作执行和 chunk 间隙，并非每次更新都与推理重叠。Rollout／Env 采用训练并行时的 355 个完整三动作 chunk，排除每个 episode 首尾 chunk；子项不重复加入父模块，P95／最大值不能逐项相加。

## 核心结果

### 1. Learner：网络训练与单 GPU 竞争

- **统计范围**：下表单位为 ms，每格依次为“均值 / P95 / 最大值”。Batch 按每次调用的采样与准备之和统计；Actor 只统计实际更新的调用。预热单项排除首次更新，网络 step 排除首个 step；首个网络 step 为 309.72 ms，150 次预热更新墙钟约 2.43 秒。

| 指标 | 预热阶段 | 在线 RL－模型未推理 | 在线 RL－模型推理中 |
|---|---:|---:|---:|
| Batch 处理（采样与准备） | 2.76 / 5.19 / 7.03 | 3.28 / 4.97 / 29.31 | 5.59 / 27.02 / 96.44 |
| 单次 Critic 更新 | 4.23 / 7.17 / 10.43 | 4.11 / 5.28 / 9.30 | 4.46 / 7.68 / 11.18 |
| 单次 Actor 更新 | 4.49 / 6.92 / 9.11 | 4.13 / 5.41 / 18.30 | 5.13 / 14.75 / 20.90 |

- **网络更新范围**：一个网络 step 包含 8 次 Critic、2 次 Actor 及 Batch 处理等更新开销，不含权重同步。目标网络每次 Critic 更新调用后软更新一次，`target_update_freq=1`、`tau=0.005`；该操作仅加权更新参数，不做前向或反向传播。

## 结论与采用方案

- **采用配置**：后续在线 RL 以 `continuous_tracking=false`、前台 20 Hz 为主。true／false 的推理、网络更新与常规实时循环总体接近；false 目标更新间隔略稳定。训练并行时网络 step 均值由未推理阶段的 67.91 ms 增至 92.64 ms，存在整体变慢及少量长尾，与单 GPU 资源竞争相符。

# 5. 推理启动：模型加载与首次预热（2026-10-31）

# 6. 在线训练中 Actor loss 与 Q 下降的分析

## 测试条件

- **配置与口径**：讨论对象为本次在线训练的平均 Q 与 Actor loss 趋势，目标为 `actor_loss = 5 × BC loss − 0.1 × Q`。Q 是 Critic 对采样状态下 Actor 所生成动作的预期折扣回报估计；Critic loss 则衡量 Q 预测与 TD 目标的误差，两者不能混为一谈。

## 核心结果

- **已观察现象**：Actor 输出动作的平均 Q 持续下降，使 `−0.1Q` 项持续上升，是本次 Actor loss 上升的主要原因。
- **可能原因一：估值修正（评分变了）**：相同状态、相同动作原先被高估，Critic 后续纠偏使 Q 降低，实际回报未必变差。早期整体高估与 Actor 利用局部高估后被纠正，都属于这一类。
- **可能原因二：策略退化（动作变差了）**：在相同状态下，Actor 后来生成的动作真实预期回报更低；Critic 若能反映这一变化，Q 就会下降。
- **可能原因三：采样分布变化（采到的数据变了）**：Replay 窗口固定时，后期失败轨迹增多并替换早期数据，可能使低价值状态占比上升，从而拉低平均 Q；即使固定 Critic、Actor，也可能出现这一趋势。关键是窗口内低价值数据的占比持续增加，而非失败总数增加或单个 batch 的随机波动。
- **Q 下降表示什么**：当前 Critic 对采样状态下 Actor 动作的平均评分越来越低。它不直接等于机械臂性能下降，因为评分标准和采样状态也会变化。
- **Q 最后是否必须上升**：不必须。如果之前高估，Q 可以下降到接近实际回报的水平后稳定；如果策略、评估状态分布和估值都趋于稳定，平均 Q 通常也应趋于稳定。Q 上升后稳定、下降后稳定或先降后升再稳定，都可能对应正常训练。

## 结论与采用方案

- **如何判断 Q 曲线**：Q 的升降不能单独判断训练好坏。机械臂实际表现改善、Q 趋于稳定且接近实际折扣回报，才支持训练取得了良好效果；Q 稳定但机械臂表现差，也可能只是停在较差策略上。Q 下降会推高 Actor loss，但不能据此直接判定优化错误。
- **已有证据与边界**：11 月 3 日续训的交叉对比支持第三类原因是平均 Q 下降的主要来源，见[实验总结](实验总结.md)。这尚未解释失败增多的根因，也不证明 Critic 对每个动作都准确；三类原因可以同时存在。
