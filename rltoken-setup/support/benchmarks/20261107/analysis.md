### 3. Chunk 切换与 min 参数说明

- 源码在每个循环判断 `current_chunk_index >= min_exec_horizon`，并非只控制首次推理。采用新 chunk 时，索引初始化为实际延迟步数，因此跳过的步数也计入这个门槛。
- 本次稳态跳过 2 步，`min=2` 已满足，采用 B 后即可请求 C；实际通常执行 B3、B4 后采用 C，从 C3 开始。模型结果就绪后在动作边界切换，不要求把旧 chunk 走完。
- 实际例子：以 chunk20（A）采用为 0 ms，7.78 ms 请求 chunk21（B），12.80／56.87 ms 开始处理 A3／A4；66.24 ms B 预测完成，99.82 ms 采用 B。106.75 ms 请求 chunk22（C），111.32／155.24 ms 处理 B3／B4；165.19 ms C 预测完成，198.02 ms 采用 C。动作编号在此从 1 开始，日志索引从 0 开始；处理时间不表示末端到达目标。
- 若改为 `min=5`，假设仍跳过 2 步，则须先执行 B3、B4、B5 才能请求 C，推理期间继续执行 B 的后续动作。这是源码逻辑说明，**本日未将 min 改成 5，也未做该配置真机测试**。
- [RTC 原论文 §4.3／Algorithm 1](https://arxiv.org/html/2506.07339v1#S4.SS3)同样在新 chunk 可用时替换旧计划，发起下一轮推理仍受最小 horizon 约束；[附录 A.4](https://arxiv.org/html/2506.07339v1#A1.SS4)真机参数为 min=25，不是我们使用的 2。这里依据的是 RTC 论文，不能误称为 RL Token 原文的调度规定。
