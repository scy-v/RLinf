# 测试进展

## ● 2026-10-31

### 1. 功能与配置更新

- RLinf 的 UR 键盘接管改为逐 action 判断，与 Franka SpaceMouse 的逐步覆盖方式对齐：按住控制键覆盖当前动作，松开后恢复原 chunk 对应位置的模型动作，同一 chunk 内可再次接管；保留按键映射、粗细步长及人工动作入库逻辑。

### 2. 问题修复

- 在线 RLT 的加载、合成观测预热和首次推理进度提示改为在 `runner.timing_mode=basic` 和 `detailed` 下均显示，避免 basic 模式长时间没有阶段反馈；细分启动诊断仍仅在 detailed 下记录，disabled 保持关闭。

### 3. 测试与验证

- 键盘映射、chunk 中途接管／释放／再次接管及实际干预 wrapper 共 23 项 CPU／假键盘测试通过；另 5 项 transition 转换、RLT 入库及成功停止回归通过。入库回归首次受沙箱 Gloo 本地通信限制报错，允许本地通信后两项均通过；Ruff lint／format 检查通过，尚未进行真机验证。
- CPU 上加载计时、终端精简显示及计时模式相关 15 项测试通过，Ruff 检查通过。运行 `20261031-214127` 的完整日志在 21:43:36 记录冻结 checkpoint 加载完成；本次显示修复尚未在新启动的真机进程中验证。
- 核对 RLinf 官方 Franka RLT 调用链：环境逐步获取观测，但训练按原始 chunk 组织 transition，未实现论文 stride=2 的重叠取窗；SpaceMouse 每个 action 判断接管，未干预位置沿用本轮模型动作，入库时仅将干预位置的 reference 替换为实际人工动作。依据：[环境执行](https://github.com/RLinf/RLinf/blob/main/rlinf/envs/real/env.py#L360)、[RLT 入库](https://github.com/RLinf/RLinf/blob/main/rlinf/workers/actor/fsdp_rlt_ac_policy_worker.py#L559)、[reference 覆盖](https://github.com/RLinf/RLinf/blob/main/rlinf/algorithms/rlt/transition.py#L57)。
- 核对 [RLToken 原文第 V 节](https://arxiv.org/html/2604.23073v1#S5)：stride=2 从中间观测起取后续连续 C 步真实动作，窗口可跨推理边界；论文未明确额外窗口是在执行中逐渐组成，还是 episode 结束后统一构造。逐步组装与最终统一取窗在起点、动作处理及终止边界一致时可得到相同完整样本，不能由 stride 推断必须等待整轮结束。
- 静态检查其他复现：openpi-RLT 支持按配置在 episode 结束后重建连续动作窗口；RL-Token-Pi05-open 在线实际补充 stride=2 窗口；Evo-RLT 的离线缓存支持间隔 2 步，在线 collector 仍按 C 步组样本；yknxh/rlt-openpi 虽提供 strided 接口，在线采集未调用。上述仅为公开源码核对，未运行这些仓库；入口分别见 [openpi-RLT](https://github.com/Yyshadow/openpi-RLT/blob/main/rlt_online_rl/README.md#replay-windows)、[Pi05-open](https://github.com/Zhengsw03/RL-Token-Pi05-open/blob/main/scripts/train_rlt_stage2_pi05.py#L4265)、[Evo-RLT](https://github.com/MINT-SJTU/Evo-RLT/blob/main/src/evo_rlt/adapters/lerobot/online_collector.py)、[rlt-openpi](https://github.com/yknxh/rlt-openpi/blob/main/src/rlt_openpi/rollout/rollout_worker.py#L205)。
- EXPO-FT 当前共享仓库按真实执行动作逐步记录，人工接管清空剩余模型计划；默认同步训练在 episode 结束时批量入库，也支持逐步更新前入库并回填动作窗口。其原论文描述为只覆盖干预位置、保留其余旧动作；此差异是本次代码与论文对照所得，未找到作者对此差异的说明，不能据当前 main 确定论文实验版本。依据：[当前循环](https://github.com/pd-perry/expo-ft/blob/main/train_pi_robo.py#L340)、[入库与回填](https://github.com/pd-perry/expo-ft/blob/main/expo_ft/data/replay_buffer.py#L282)、[原论文](https://arxiv.org/html/2605.25477v2)。

### 4. 待解决问题与下一步

- 本阶段按 RLinf 的 RLT 路径完成复现：保留非重叠 chunk、逐步人工覆盖及松开后恢复旧 chunk 后续动作，暂不引入丢弃旧计划重推或 stride=2 重叠取窗；论文的数据扩展作为已知未实现项，后续可单独对比。
- 下一次真机运行验证 chunk 中途按键接管、释放后恢复对应模型动作及再次接管，并检查人工动作与 reference 的入库位置；本次修改尚不能证明真机响应延迟或训练效果改善。

## ● 2026-10-30

### 1. 功能与配置更新

- 在线 UR 采用 `env.train.override_cfg.step_frequency=20.0` Hz、`continuous_tracking=false` 作为后续实验配置，每个执行 chunk 保持 3 个动作。前台更新节拍与后台 PD 频率分开配置，RLinf 纯推理及仓库内 VLA-Precision 沿用各自的频率参数。
- 在线 RL、RLinf 纯推理与仓库内 VLA-Precision 的 true／false 两种模式统一按前台动作提交节拍调度：true 发布目标位姿，false 下发该 action 计算的力／力矩。新增 `target_interval_ms`／原生推理 JSONL 的 `target_interval_sec`；保留 `action_interval_ms` 的 step 入口含义，`control_ms` 改按单次调用理解，不能作为更新周期。
- 旋转 PD 改为直接使用增益，不再把力矩除以控制频率；三套 100 Hz 配置的旋转 P／D 从 2000／400 等效转换为 20／4。旧自定义配置需将旋转增益除以原控制频率后迁移，后台频率仍控制循环节拍。

### 2. 问题修复

- 原节拍只在底层 step 中间补足周期，后续观测和外层处理会叠加到相邻动作间隔。现按上次提交时间安排下一次提交，读取状态前参考前次准备耗时等待，下发前再次检查节拍；超时后不补发追赶，每个 chunk 最后目标保持一个周期后再读取最终观测。后台目标应用确认及 Learner 更新顺序保持原行为。
- `control_overrun_sec` 改为目标提交间隔超过设定周期的部分，chunk 首个动作没有间隔时记 0；细粒度计时关闭时跳过新增诊断等待累加和间隔计算，保留控制调度必需的本地读钟，不添加计时专用设备或跨进程同步。

### 3. 测试与验证

- 真机日志 `20261030-202810`（true）与 `20261030-211110`（false）分别复核 4／5 个 episode。20 Hz 下全部可用目标间隔均值／P95／最大值分别为 50.38／52.09／54.23 ms 和 50.19／51.86／52.27 ms；true 后台实际约 99.31 Hz。常规训练并行 chunk 的 Rollout 均值 81.29／81.55 ms，Env 均值 181.51／179.33 ms；未见模式切换造成持续实时退化，分段延迟与三阶段网络时间见[性能摘要](summary.md)及[分类对比](support/benchmarks/20261030/true_false_20hz_classified_comparison.json)。
- 旋转增益新增 15 项等效性用例通过，覆盖 50／100／200 Hz 与 true／false，确认改频率不再直接缩放力矩；此前相关回归 137 项通过。节拍修复最终通过 106 项 UR 环境／推理、30 项机械臂接口及 21 项计时日志测试，均使用 CPU／假 SDK；Ruff 通过。两类已有异步退出测试曾阻塞，本轮未重新运行，不能记为全量通过。详见[增益验证](support/benchmarks/20261030/ur_rotational_gain_decoupling_validation.json)、[节拍验证](support/benchmarks/20261030/ur_action_cadence_validation.json)。
- 无硬件启动探针将约 0.37 秒首动作延迟定位到 Rollout→Env 路径上两次惰性通信组初始化；episode 首次提交还受到通信初始化和原有 1 秒 Learner 轮询影响。未完整复现此前 1.43 秒首动作及 6～7 秒首轮入库长尾，不把探针结果作为原运行的完整归因；见[启动定位记录](support/benchmarks/20261030/startup_delay_findings.json)。

## ● 2026-10-29

### 1. 功能与配置更新

- UR 在线 RLT 默认开启 `env.train.flush_replay_on_episode_end=true`：成功或超时停止后，使用复位前终止观测补齐末条 transition 的下一状态特征，按实际 episode 长度提交；actor 确认入库后才复位，没有关键阶段数据也正常确认。设为 `false` 恢复每 `max_chunks_per_rollout_epoch=50` chunks 提交，当前训练 `max_episode_chunks=200`、`rollout_epoch=1`，eval 保留 20/200。
- 新增 `runner.timing_mode=disabled/basic/detailed`，默认 `basic`；关闭模式停用新增的 Actor、Rollout、Env 计时、计时线程和计时文件写入，保留 RLinf 原有日志及控制节拍。删除旧 `runner.timing_enabled` 及其兼容映射，计时统一由 `runner.timing_mode` 控制。
- `basic` 保留 Learner 的采样、准备、独立 critic、独立 actor、target 和整次更新时间，并记录 Rollout 的输入处理／推理／动作发送／训练数据提交，以及 Env 的输入处理／动作执行／反馈发布。两个 worker 的 `work_ms` 分别为大模块之和，排除上游等待、episode 收尾和复位。
- `detailed` 增加 Rollout 的预处理、KV cache、z 编码、参考动作、MLP 与输出整理，Env 的动作准备、chunk 执行、结果整理、请求／transition 构建和发送，并保留 action、后台 PD、动作间隔、终止推理、Runner step 等诊断；子项及并行 PD 不重复计入大模块。新增计时采用本地主机经过时间，不添加设备同步或跨进程等待，输出仍为 `timing.log`／`timing.tsv`。
- 默认 `rollout.rlt_inference_warmup.enabled=true`，在环境初始化和首次复位前用合成观测预热三次，不下发动作，保留原随机状态；设为 `false` 恢复首次实际推理时初始化。终端警告改为较淡红色，错误保留醒目提示。

### 2. 问题修复

- episode 提交按成功／超时信号收尾，避免运动中固定批次边界重复推理；补齐下一状态特征放在停止后、复位前。人工成功沿用 `_stop_for_success()` 的观测刷新，超时沿用完整 chunk 末尾观测，移除外层重复 `observe()`；关键阶段筛选、人工干预和持续训练保持原行为。
- 入库确认核对本轮末条 chunk 标识，错配、取消或停止均不触发复位；异常或 `Ctrl+C` 中断的未完成 episode 不提交，退出仍停止力控。
- 首次启动失败定位为 checkpoint 加载与精度转换的主机内存峰值，并非把预热移到复位前会改变推理。ZIP checkpoint 使用 `torch.load(..., mmap=True)`，旧格式保留回退路径，模型参数存储及加载语义保持不变。
- 去掉新增分段计时引入的设备同步，关闭模式也跳过 UR action trace、后台 PD 诊断数据及新增进度计时；训练更新顺序、原有必要同步和控制线程节拍保持原行为。新旧计时口径不同，历史同步计时不能直接作为新字段的 GPU 完成时间。

### 3. 测试与验证

- episode/replay 阶段的数据回归 178 项、UR/RLT 与停止流程 48 项 CPU／假硬件测试、参数与 chunk 上限 13 项通过。已有 VLM 视频元数据用例因本机 `VideoMetadata` 不接受 `frames_indices` 排除；此前全量工具检查因 Ray 启动超时中止，不能记为全量通过。

## ● 2026-10-26

### 1. 功能与配置更新

- RLinf UR 推理与在线 RL 均支持两种力控模式：`continuous_tracking=false` 每条 action 计算并发送一次力；`true` 前台更新绝对目标，后台以 100Hz 为目标频率读状态、重算力并调用 `forceMode`，推理等待期间继续跟踪最后目标。
- 仓库内 VLA-Precision 推理新增 `robot.force_mode.continuous_tracking`，在自身后端实现后台跟踪；目标首次发送成功后才确认，避免被后续目标覆盖。
- 当日默认：两套推理为 `true`，UR 在线 RL 为 `false`。同名开关属于本地 UR 适配，上游 Franka 使用 Franky/libfranka 阻抗控制。
- 新增后台实际发送频率统计，区分 chunk 内 action 频率与含推理等待的整体吞吐；复位和暂停不计入后台频率。

### 2. 问题修复

- 修复 episode 开始前持续力控已运行的问题：启用 `start_paused=true`，推理按 Enter 后启动，在线 RL 收到第一条 action 后启动；当日在线 RL 尚未增加 Enter 门控。
- 成功、超时或异常后停止力控并跳过 chunk 剩余动作。复位必须先确认后台线程退出，再回位、设置载荷和清零；`forceModeStop` 失败时中止后续复位操作。
